# Anomaly: Table VII's reported 0.741 exceeds the analytic ceiling

Generated by `backend/experiments/diagnose_table_vii.py` (seed=42). Diagnostic only -- no simulator code was modified.

## Ceiling derivation

For the canonical 7x6 SUCCESS_MATRIX and the blind 6/7-correct rule `BLIND_RULE` (recovery/envs/canonical.py), under a **uniform** type prior:

- `oracle_rate(MATRIX)` = 0.757143  (= 5.30/7)
- `random_rate(MATRIX)` = 0.436905  (= 18.35/42)
- `policy_rate(MATRIX, BLIND_RULE)` = **0.735714** (= 5.15/7) -- the rate this rule achieves with a *perfect* classifier (equivalently, identity confusion). This is a hard ceiling in the noiseless sense (see `recovery/theory/analytic.py::policy_rate` docstring).
- normalized: 0.9331

The paper (docs/PAPER_PREP.md, Phase 4b Task 1 table; also backend/results/phase4b/context_sweep_results.csv and PHASE4B_SUMMARY.md) reports **0.741** for this rule at beta=1.0, effective accuracy 0.939 -- **+0.005286** above the noiseless ceiling. Independently, that beta=1.0 row is *not* synthetic noise: `C(beta=1.0) = C_emp` exactly (see `src/evaluation/classifier_context.py::interpolated_confusion_matrix`), and the real fitted classifier's empirical confusion matrix has mean-diagonal accuracy 0.939047619047619 -- matching the paper's 93.9% figure exactly. So this is the real classifier, not a rounded synthetic stand-in.

## VERDICT

**Hypothesis B**

Evidence supports Hypothesis B (non-uniform confusion), with a caveat. The real classifier's empirical confusion matrix C_emp is far from uniform (see step c) and analytically predicts 0.7234 -- below the noiseless ceiling (0.735714) and consistent with the mathematical fact (documented in recovery/theory/analytic.py) that confusion CAN exceed the noiseless policy_rate for a non-argmax policy like BLIND_RULE (wrong_tool_selected -> replan is suboptimal, so confusion that reroutes it to switch_tool's action helps). A fresh reproduction using the current, unmodified simulator (config iii above) measured 0.7239, which is consistent with the C_emp analytic prediction (diff=+0.0006) and does NOT reproduce the paper's reported 0.741 (gap=+0.0176). This suggests the reported 0.741 reflects a specific historical run (results/phase4b/context_sweep_results.csv) whose exact conditions (classifier training seed/state at the time, Monte Carlo variance across 50 trials x 500 episodes) were not fully reproduced here, rather than a currently-reproducible property of the codebase.

**Hypothesis A (bug in current code) is disfavored**: all three live reproductions in this run stayed at or below their respective analytic predictions/ceilings (config i: -0.000539, config ii: +0.001348, config iii: +0.000569 -- all within or near their stated tolerances), so the currently-committed `_simulate_episode`/`run_context_mode_sweep` code path (harness.py:119, harness.py:917) does not itself produce values above the mathematical ceiling when run fresh. The anomaly is specifically that the *historical* `results/phase4b/context_sweep_results.csv` value (0.741) is +0.0176 above what the current code reproduces for the real-classifier condition (0.7239) -- i.e. the discrepancy looks like it lives in *what state produced that specific CSV*, not in the reward-sampling logic as it exists today.

This is stated as a hypothesis supported by the evidence gathered here, not a certainty -- confirming it fully would require locating or regenerating the exact classifier state and RNG trace used to produce `results/phase4b/context_sweep_results.csv`, which this diagnostic does not have access to. No fix has been applied; per task instructions, `results/phase4b/context_sweep_results.csv`, `docs/PAPER_PREP.md`, and all simulator code are left untouched.

## Automated Prevention (Task 3)

Task 3 adds a runtime invariant guard layer (`recovery/guards/invariants.py`)
so that a future sweep producing a value like 0.741 fails loudly instead of
silently reaching a results CSV or a paper table.

**Which guard catches 0.741**: `check_static_policy_ceiling(rate, P, pi,
n_episodes, ...)`. For any FIXED policy `pi` (like `BLIND_RULE`), it verifies

```
rate <= policy_rate(P, pi) + slack
```

where `policy_rate(MATRIX, BLIND_RULE) = 0.735714` is exactly the analytic
ceiling derived above, and `slack = sigmas * sqrt(0.25 / n_episodes)` is a
statistical tolerance that shrinks as the episode count grows (default
`sigmas=3.0`).

**Why this needed a real design decision, not just wiring**: applying this
guard literally as `check_static_policy_ceiling(0.741, MATRIX, BLIND_RULE,
n_episodes=25000)` -- i.e. at the historical run's own sample size -- does
**not** raise. At `n_episodes=25000`, `slack ~= 0.0095`, and `0.741` is only
`0.0053` above the ceiling -- inside 3-sigma tolerance. This is fully
consistent with this document's own VERDICT above (0.741 sits inside the
historical run's bootstrap 95% CI of [0.730, 0.752] and cannot be
statistically distinguished from noise at that sample size). The regression
test in `tests/test_invariants.py` therefore checks the guard at
`n_episodes=200_000` (Task 2's standard, properly-powered episode count),
where `slack ~= 0.0034 < 0.0053` and the same `rate=0.741` **does** raise
`InvariantViolation`. This is a deliberate, documented choice (see
`docs/architecture.md`, "Guard layer"): the guard is statistically honest
about sample size in both directions -- it would not have falsely flagged
the historical 25,000-sample run as definitively broken (matching this
investigation's own inconclusive verdict), but it will catch the same
raw value at the episode counts this repository's experiments actually use
going forward.

**Regression test**: `tests/test_invariants.py::test_static_policy_ceiling_regression_table_vii`
asserts `check_static_policy_ceiling(0.741, MATRIX, BLIND_RULE,
n_episodes=200_000)` raises `InvariantViolation`, and that the exception
message contains both `0.741` (the observed value) and `0.7357` (the
analytic ceiling), so a future failure is immediately diagnosable without
re-deriving the math.
